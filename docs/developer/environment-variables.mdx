Core environment variables are centralized in `api/constants.py`. Variables marked **Required** in the description must be explicitly set — the application will either fail to boot or behave insecurely without them.

## Deployment Modes

LightMove.ai supports two deployment modes, set via `DEPLOYMENT_MODE`:

- **OSS**: The default mode. Designed for self-hosted deployments using [Docker Compose](/deployment/docker) — the fastest way to get LightMove.ai running. Uses local JWT authentication and MinIO for storage.
- **SaaS**: Intended for customised deployments outside of Docker. Authentication and API key management are handled through Dograh Managed Platform Services (MPS, the upstream service LightMove.ai is built on), allowing greater flexibility in how the platform is hosted and integrated.

The relevant required variables for each mode are noted in the descriptions below.

## Credential encryption

Workspace credentials (API keys, bearer tokens, passwords and integration connection keys used by tools and webhooks) are encrypted at rest with [Fernet](https://cryptography.io/en/latest/fernet/) when keys are configured.

| Variable | Default | Description |
|---|---|---|
| `CREDENTIALS_ENCRYPTION_KEYS` | unset | Comma-separated Fernet keys. The first key encrypts; every key decrypts. Encrypts workspace credentials, telephony provider credentials, integration connection details and organization configuration values at rest. **Required when `ENVIRONMENT` is `production` or `DEPLOYMENT_MODE` is not `oss`.** In local development and tests, unset stores them in plaintext and logs a warning at startup |

The API and the background worker check this at startup and refuse to start when:

- a key is not a valid Fernet key;
- the keys are unset but encrypted values already exist (any mode);
- the keys are unset and `ENVIRONMENT` is `production` or `DEPLOYMENT_MODE` is not `oss`;
- the keys are set but cannot decrypt an existing encrypted credential (a key that wrote stored rows was removed).

Generate a key with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` and set the same value on every API and worker process.

- **Enabling:** set the key and run migrations — existing plaintext rows are encrypted by the migrations. If the key is added after migrating, or migrations are applied offline (`alembic upgrade --sql`, which refuses to run with keys set), run `python -m scripts.reencrypt_credentials` once (reads accept plaintext rows meanwhile).
- **Rotating:** set `CREDENTIALS_ENCRYPTION_KEYS=<new>,<old>` and restart, run `python -m scripts.reencrypt_credentials` (re-seals all four encrypted columns), then set `CREDENTIALS_ENCRYPTION_KEYS=<new>` and restart again.

<Warning>
Back the keys up with your database backups. Losing every key that encrypted a credential makes it unreadable, and removing the key while encrypted credentials exist breaks the tools and webhooks that use them.
</Warning>

## Integrations (tools service)

[Integrations](/voice-agent/tools/integrations) such as Google Calendar, Google Sheets and the website catalogue run in a separate service, `fallcha-tools` (the `tools/` folder), which the API calls over the internal network. Set these on the **API**:

| Variable | Default | Description |
|---|---|---|
| `TOOLS_SERVICE_URL` | `http://fallcha-tools:8000` | Internal URL of the tools service. Change it only when the service runs elsewhere (for example `http://localhost:8010` when both run on your machine) |
| `TOOLS_INTERNAL_SECRET` | unset | Shared secret the API sends to the tools service. **Must equal the tools service's value.** While unset, the integrations API answers `503 tools_service_not_configured` |
| `TRUSTED_TOOL_HOSTS` | unset | Comma-separated origins (`scheme://host[:port]`) that user-configured service URLs (for example an HTTP API tool's URL) may target even though they are internal. Only matters when `DEPLOYMENT_MODE` is not `oss`: OSS mode applies no URL restriction. Trust is per exact scheme, host and port; entries naming `localhost` or an IP literal are ignored. The `TOOLS_SERVICE_URL` origin is trusted automatically once `TOOLS_INTERNAL_SECRET` is set |

And on the **tools service**:

| Variable | Default | Description |
|---|---|---|
| `DATABASE_URL` | N/A | **Required.** The same Postgres as the API. The service only uses its own `fallcha_tools` schema and migrates it on start |
| `TOOLS_ENCRYPTION_KEYS` | N/A | **Required.** Comma-separated Fernet keys encrypting connection secrets and Google tokens. The first key encrypts; every key decrypts |
| `TOOLS_INTERNAL_SECRET` | N/A | **Required.** At least 16 characters, same value as the API's |
| `TOOLS_PUBLIC_BASE_URL` | `PUBLIC_BASE_URL` (Docker Compose) | Public URL that reaches the service's `/oauth/<provider>/callback`. Google OAuth redirect URIs are built from it. While unset, OAuth is off, for the platform client and workspaces' own clients alike (service accounts still work) |
| `TOOLS_UI_RETURN_URL` | `PUBLIC_BASE_URL/integrations` (Docker Compose) | The UI page the OAuth callback sends the browser back to. While unset, OAuth is off |
| `TOOLS_GOOGLE_CLIENT_ID` | unset | Optional platform Google OAuth client (it can be the same client as Google sign-in). When set with `TOOLS_GOOGLE_CLIENT_SECRET`, every workspace can connect Google Calendar and Sheets with one click; workspaces can still use their own client. Set both or neither. The client must list `TOOLS_PUBLIC_BASE_URL/oauth/google-calendar/callback` and `.../google-sheets/callback` as redirect URIs |
| `TOOLS_GOOGLE_CLIENT_SECRET` | unset | The platform Google client's secret, stored encrypted. Changing it updates the client in place. Changing `TOOLS_GOOGLE_CLIENT_ID` offers the new client from then on, while existing connections keep refreshing with the old one |

The service refuses to start without its three required variables, or with only one of the two `TOOLS_GOOGLE_*` variables; the rest of the stack keeps running. `scripts/setup_local.sh`, `scripts/setup_local.ps1`, `scripts/setup_remote.sh` and `saas/dev/bootstrap-env.sh` generate `CREDENTIALS_ENCRYPTION_KEYS`, `TOOLS_ENCRYPTION_KEYS` and `TOOLS_INTERNAL_SECRET` when they are missing, and never replace a value that is already set.

<Warning>
Docker Compose pulls the tools service as `${REGISTRY}/fallcha-tools`, alongside `dograh-api` and `dograh-ui`. The registry must publish that image. LightMove.ai's release workflow and `deploy/gcp/cloudbuild.yaml` do. Public upstream Dograh registries do not, so an install pointing `REGISTRY` at them gets no tools service. Either set `REGISTRY` to a registry holding all three images, or build it locally (`docker compose build fallcha-tools`, or `setup_remote.sh` in build mode).
</Warning>

<Note>
On a remote install, nginx forwards only `/oauth/<provider>/callback` to the tools service and does not write that request's query string (which carries the authorization code) to its access log. Everything else in the tools service is reachable only from inside the Docker network.
</Note>

## Authentication (OSS)

| Variable | Default | Description |
|---|---|---|
| `OSS_JWT_SECRET` | N/A | **Required for OSS deployments.** Secret used to sign JWT tokens. Must be set to a strong random value in production |
| `OSS_JWT_EXPIRY_HOURS` | `720` | JWT token lifetime in hours (default: 30 days) |
| `ENABLE_SIGNUP` | `true` | Set to `false` to disable public signup on invite-only installs — `POST /api/v1/auth/signup` returns 403 and the login page hides the Sign up link |
| `REQUIRE_EMAIL_VERIFICATION` | `true` | Password signups must confirm their email address before they can log in. Needs a working `EMAIL_PROVIDER`; with `none` the message is only written to the API log |
| `GOOGLE_CLIENT_ID` | `null` | Google OAuth client id. With `GOOGLE_CLIENT_SECRET`, shows "Continue with Google" on the login and signup pages |
| `GOOGLE_CLIENT_SECRET` | `null` | Google OAuth client secret. Keep secret |
| `GOOGLE_REDIRECT_URI` | `UI_APP_URL` + `/auth/google/callback` | Must be listed as an authorized redirect URI on the Google OAuth client. Only for running the API outside Docker: `docker-compose.yaml` does not pass it through, so containers always use the default |

<Warning>
Never use the placeholder `OSS_JWT_SECRET` in a production deployment. Generate a strong random secret and store it securely.
</Warning>

| Variable | Default | Description |
|---|---|---|

| `EMAIL_FROM` | `LightMove.ai <no-reply@localhost>` | Sender address. With Resend it must be on a verified domain; until then use `onboarding@resend.dev`, which only delivers to the Resend account owner's address |

| `SMTP_HOST` | `null` | **Required for `smtp`.** SMTP server host |
| `SMTP_PORT` | `587` | SMTP server port |
| `SMTP_USERNAME` | `null` | SMTP username |
| `SMTP_PASSWORD` | `null` | SMTP password |
| `SMTP_SECURITY` | `starttls` | `starttls`, `ssl` or `none` |
| `SMTP_TIMEOUT_SECONDS` | `15` | SMTP connection timeout |

<Tip>
For local development, `docker-compose-local.yaml` runs Mailpit. Set `EMAIL_PROVIDER=smtp`, `SMTP_HOST=localhost`, `SMTP_PORT=1025` and `SMTP_SECURITY=none`, then read the mail at http://localhost:8025.

| `PUBLIC_BASE_URL` | `null` | Canonical public origin for the deployment (scheme + host, e.g. `https://203-0-113-10.sslip.io`). For a standard single-host install this is the only endpoint value you set — `BACKEND_API_ENDPOINT` and `MINIO_PUBLIC_ENDPOINT` derive from it |

| `MPS_API_URL` | unset | Upstream Dograh Model Proxy Service (MPS) URL. | `DOGRAH_MPS_SECRET_KEY` | `null` | **Required for non-OSS deployments.** Secret key for authenticating with MPS |
| `CORS_ALLOWED_ORIGINS` | `null` | Comma-separated list of origins allowed to make credentialed cross-origin requests (e.g. `https://app.example.com,https://admin.example.com`); `*` is refused. Unset in local OSS development, any origin is allowed without credentials. The embed widget's `/api/v1/public/embed/*` endpoints handle CORS themselves, per embed token's allowed domains |

## Storage

LightMove.ai uses **MinIO by default**, which is bundled with the self-hosted deployment and requires no external setup. Set `ENABLE_AWS_S3=true` to switch to AWS S3 — typically used for cloud or managed deployments where S3 is already part of the infrastructure.

### MinIO (OSS default)

| Variable | Default | Description |
|---|---|---|
| `MINIO_ENDPOINT` | `localhost:9000` | MinIO server host and port |
| `MINIO_PUBLIC_ENDPOINT` | `PUBLIC_BASE_URL`, else `http://localhost:9000` | Origin (scheme + host, no path) browsers use to reach MinIO; presigned download and upload URLs are signed for it. Derives from `PUBLIC_BASE_URL`; set explicitly only for a separate object-storage origin |
| `MINIO_ACCESS_KEY` | N/A | **Required for OSS deployments.** MinIO access key. Must be set to a secure value in production |
| `MINIO_SECRET_KEY` | N/A | **Required for OSS deployments.** MinIO secret key. Must be set to a secure value in production |
| `MINIO_BUCKET` | `voice-audio` | Bucket name for audio files |
| `MINIO_SECURE` | `false` | Use HTTPS for MinIO connections |
| `MINIO_REGION` | `us-east-1` | Region MinIO signs requests (and presigned URLs) for. Must match the MinIO server's `MINIO_REGION`; MinIO's default is `us-east-1` |

### AWS S3 (alternative)

| Variable | Default | Description |
|---|---|---|
| `ENABLE_AWS_S3` | `false` | Set to `true` to use AWS S3 instead of MinIO |
| `S3_BUCKET` | `null` | S3 bucket name |
| `S3_REGION` | `us-east-1` | AWS region |
| `S3_ENDPOINT_URL` | `null` | Custom S3 endpoint for S3-compatible servers (e.g. `https://s3.example.com`). Leave unset for AWS. |
| `S3_SIGNATURE_VERSION` | `null` | Signing version. Unset uses botocore's default; set `s3v4` for servers that require SigV4. |
| `S3_ADDRESSING_STYLE` | `null` | `auto` (default), `path`, or `virtual`. Many S3-compatible servers and TLS setups require `path`. |

Credentials come from the standard `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` environment variables.

#### S3-compatible servers (MinIO, rustfs, Ceph, ...)

The S3 backend can target any S3-compatible server, not just AWS. Both backends keep the bucket private and hand browsers presigned URLs; the S3 backend adds custom endpoints, signature versions and addressing styles.

To use it, set `ENABLE_AWS_S3=true` and point it at your server with the `S3_*` overrides above. For example, against [rustfs](https://github.com/rustfs/rustfs):

```bash
ENABLE_AWS_S3=true
S3_BUCKET=voice-audio
S3_REGION=us-east-1
S3_ENDPOINT_URL=https://s3.example.com
S3_SIGNATURE_VERSION=s3v4   # rustfs rejects SigV2 with SignatureDoesNotMatch
S3_ADDRESSING_STYLE=path    # rustfs and most non-AWS TLS certs require path-style
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
```

<Note>
Presigned URLs point at `S3_ENDPOINT_URL`, so that host must be reachable from the browser. Because browsers fetch transcripts cross-origin, the bucket also needs a CORS rule allowing your app's origin for `GET`/`HEAD` — configure this on the storage server (e.g. via `PutBucketCors`), not in LightMove.ai.
</Note>

## Telephony

Carriers dial the media WebSocket back at `/api/v1/telephony/ws/{workflow_id}/{organization_id}/{workflow_run_id}`. Those ids travel in a caller-visible URL, so on their own they are a guessable capability. Setting a secret makes LightMove.ai sign that URL with an HMAC and verify the signature when the socket opens.

The signature travels as a trailing path segment — `/api/v1/telephony/ws/{workflow_id}/{organization_id}/{workflow_run_id}/{token}` — because carriers do not reliably forward query strings. Twilio [documents that its `<Stream>` url "does not support query string parameters"](https://www.twilio.com/docs/voice/twiml/stream) and drops them outright. Asterisk ARI is the exception: it connects to `/api/v1/telephony/ws/ari` and passes `token` as a query parameter alongside its other routing values, which works because Asterisk builds that URL itself.

| Variable | Default | Description |
|---|---|---|
| `TELEPHONY_WS_TOKEN_SECRET` | `null` | Secret used to sign the media WebSocket URL **and** the Telnyx call-events webhook URL. Unset leaves both URLs unchanged and both checks disabled |
| `TELEPHONY_WS_TOKEN_ENFORCE` | `false` | Reject connections whose token is missing or invalid (WebSocket close `4401`) |

Roll it out in two steps so no call is dropped:

1. Set `TELEPHONY_WS_TOKEN_SECRET` on **every** process that places or receives calls — the `api` service and, if you run Asterisk, the `ari-manager`. They must share the same value: one mints the token, the other verifies it. Calls keep connecting either way; anything unverifiable is logged as `UNVERIFIED media socket`.
2. Once those warnings stop, set `TELEPHONY_WS_TOKEN_ENFORCE=true` to start rejecting them.

Setting `TELEPHONY_WS_TOKEN_ENFORCE` without a secret does nothing at all — the check is skipped entirely rather than rejecting every connection.

The same secret also signs the Telnyx call-events webhook URL (`/api/v1/telephony/telnyx/events/{workflow_run_id}?token=…`), which the events route verifies before any database lookup. Unlike the media socket, that token rides in a query string: Telnyx preserves query strings on webhook POSTs. It is a bearer credential with no expiry and appears in full in access logs — the same caveat below applies.

<Note>
The signed URL is a bearer credential, and it is not hidden: the token appears in full in the `api` and nginx access logs, and in carrier-side request logs (Twilio's debugger, Telnyx's request inspector). Anyone who can read those logs can open the media socket for a run that is still in `initialized`. Treat log access as socket access.
</Note>

## Data retention

A daily background job (03:17 UTC) deletes call recordings, transcripts and call content older than each organization's **Call data retention (days)** setting, and clears widget visitor data and webhook payloads after 30 days.

| Variable | Default | Description |
|---|---|---|
| `RETENTION_PURGE_ENABLED` | `true` | Set to `false` to turn the daily retention purge off. The job then only logs that it is disabled |
| `RETENTION_PURGE_DRY_RUN` | `false` | Set to `true` to log one line per organization with the counts of runs, campaigns, queued rows, widget sessions and webhook deliveries the purge would clear, without deleting or changing anything |

## Organization deletion

When an admin deletes an organization it is closed at once and erased 30 days later by a daily background job (03:47 UTC); see [Export or delete your data](/configurations/delete-and-export-data).

| Variable | Default | Description |
|---|---|---|
| `ORG_ERASURE_ENABLED` | `true` | Set to `false` to stop the daily erasure job. Deletion requests are still accepted and stay pending (the organization stays closed) until the job is enabled again |

## Further Customisation

The variables documented here cover the standard configuration surface. For advanced customisation — such as integrating additional services or tuning internal behaviour — consult the relevant module alongside `api/constants.py` to understand how each variable is consumed.
